# 异常处理规范

本规范定义 LogiOps 平台对运输异常的识别、确认、处置与闭环口径。所有异常单必须可追溯到订单、车辆与承运商，处置动作必须留痕。

## 1.1 适用范围

- 适用于公路整车运输在途阶段发生的全部异常：车辆故障、延误风险与其他异常。位置停滞是**信号**（停滞超过阈值会触发车辆故障单），不是独立的异常类型；客户投诉不构成异常类型，应按事实归到上述类型。
- 不适用于货损货差理赔、单证与关务争议，上述场景由《货损处理办法》单独规定。
- 所有时间口径为北京时间（Asia/Shanghai），系统内部存储为 UTC。

## 1.2 异常类型

- 车辆故障（VEHICLE_BREAKDOWN）：车辆无法继续行驶，或需要停车维修、等待配件。
- 延误风险（DELAY_RISK）：按订单上登记的**预计到达时间**判定 —— 预计到达 − 承诺送达 超过该客户允许延迟时自动建单（口径 2026-10-08）。**在途不按预测 ETA 建单**，也不再等订单送达才判定；未登记预计到达时间的订单不判定延误。
- 其他（OTHER）：信息不足以归入以上两类，例如仅报告"路上有情况"。

## 1.3 等级与风险评分

- 等级**不是**凭"预计延误多久"拍的，而是由**风险分**决定；风险分只由"当前这一个异常"的问题权重 + 客户等级放大组成，两类问题**互不叠加**（车辆故障单不计延误，延误单不计车辆故障），封顶 4 分。
- 风险分构成：

| 因子（代码） | 触发条件 | 分值 |
|---|---|---|
| 延误时长（`DELAY_BASE`） | 延误 ≤ 0 分钟 | 0 |
| | 延误 1–120 分钟 | 1 |
| | 延误 121–360 分钟 | 2 |
| | 延误 > 360 分钟 | 3 |
| 车辆故障（`VEHICLE_BREAKDOWN`） | 类型为车辆故障，且车辆仍处维修/等待状态 | 1 |
| VIP 客户（`CUSTOMER_VIP`） | 客户等级为 VIP | 1 |
| SVIP 客户（`CUSTOMER_SVIP`） | 客户等级为 SVIP | 2 |

- 等级映射：0 分 = 低级（LOW）；1–2 分 = 中级（MEDIUM）；3 分 = 高级（HIGH）；4 分 = 紧急（CRITICAL）。
- 示例：VIP 客户的车辆故障 = 1 + 1 = 2 → 中级；VIP 客户延误 400 分钟 = 3 + 1 = 4 → 紧急。
- 响应时限：低级 2 小时内确认；中级 1 小时内确认；高级 30 分钟内确认；紧急 15 分钟内确认并上报值班主管。
- 风险分与等级由系统规则计算，**人工与 AI 均不得改写、不得下调**；确需上调，必须由 OPERATOR 及以上角色在异常单备注中说明理由。
- 车辆故障修复后（车辆不再处于维修中），「车辆故障」因子按**现状**消失、风险分随之下降；但系统**不会**因此自动收口异常单，仍须人工解决 / 关闭。
- 说明"风险为什么是 N 分"时，必须逐项列出上面的因子与分值，并说明客户等级是放大项而不是另一个异常。

## 1.4 处置流程

1. 识别：系统按两条规则自动建单 —— 轨迹停滞超过阈值（车辆故障）、登记的预计到达时间超时（延误）；也可在录入承运商消息后人工建单。
2. 确认：运营人员在异常详情页核对事实（位置、车辆状态、承运商反馈），把状态推进到「处理中」（PROCESSING）。
3. 分析：触发 AI 分析，输出摘要、根因建议、处置建议与依据来源；风险等级以系统规则结果为准。
4. 审批：AI 的每条写意图转为审批单，由人工批准、修改或驳回；未批准的写意图不得产生业务副作用。
5. 执行：审批通过后由后端服务执行，例如更新 ETA、创建跟进任务、保存并发送客户通知。
6. 闭环：异常解决后由人工 resolve；确认无残留影响后再 close，并选择关闭原因。

## 1.5 升级机制

- 超过响应时限未确认的异常，系统自动提醒当班 OPERATOR，并抄送 ADMIN。
- CRITICAL 异常每 30 分钟提醒一次，直到进入 PROCESSING 状态。
- 涉及 SVIP 客户或金额较大的异常，必须在 1 小时内由 ADMIN 介入，并在异常时间线中记录介入说明。

## 1.6 事实一致性要求

- 异常单上的延误分钟、是否违约、风险等级必须以系统规则计算值为准，任何人工或 AI 输出不得覆盖。
- AI 输出的处置建议如引用来源，必须指向真实存在的轨迹事件、承运商消息或知识片段。
- 发现 AI 输出与系统事实不一致时，系统必须拦截该输出并标记为失败，由人工按流程处理。

## 1.7 闭环与复盘

- 每周复盘 CRITICAL 与 SLA 违约异常，输出根因分布与承运商表现。
- 同一个客户 90 天内出现 3 次以上同类异常的，纳入客户服务改进清单。
- 同一个承运商 30 天内出现 2 次以上车辆故障的，由采购与运力管理部门约谈。

## 1.8 记录与审计

- 异常状态每次变更都写异常时间线，包含操作者、来源（人工/审批后 AI/系统）与变更前后的状态。
- 审批执行必须记录 ai_payload 与 final_payload，便于复盘"AI 建议被修改了多少"。
- 审计日志只追加不修改，保留期不少于 12 个月。

## 1.9 与其他规范的衔接

- 涉及车辆故障的处置细节，见《车辆故障处理规范》。
- 涉及延误口径与违约判定，见《客户 SLA 规则》。
- 涉及 VIP/SVIP 客户的响应与告知，见《VIP 客户服务规则》。
- 涉及客户通知文案与审批，见《客户通知规范》。
- 多篇规范同时适用时，以更严格的时限与更高的服务等级为准。
- 规范之间出现冲突时，由运营负责人裁决并在下个版本中修订。

## 1.10 常见错误做法

- 用人工填写的延误分钟覆盖系统计算值，导致 Dashboard 与复盘数据不一致。
- 仅在微信群沟通而不写入承运商消息，导致异常无法复盘、无法举证。
- 未经审批直接给客户承诺补偿，造成商务口径不一致。
- 异常长期停在「待确认」而不确认与处置，未体现"人在环上"。
- 关闭异常时不填写关闭原因，导致根因分布统计失真。
- 用"实际送达时间"解释延误，或按"预计延误多久"自拟等级 —— 延误只看登记的预计到达时间，等级只看系统风险分。
- 把"延误 + 车辆故障"两条问题叠加算风险，导致分值虚高（两类问题互不叠加）。
