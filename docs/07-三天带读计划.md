## 2. Day 1 详细计划

### 2.1 段 1 · 全局地图（✅ 本段讲解见下）

**先建立"骨架感"，不要陷入细节。** 只读 5 个文件的**关键几行**：

| 顺序 | 文件 | 看什么 |
|---|---|---|
| 1 | `backend/app/main.py` | 请求 ID 中间件、异常处理器注册、`include_router(build_router(), prefix=...)` |
| 2 | `backend/app/api/v1/__init__.py` | 路由"按固定模块名自动发现"：为什么缺文件只告警不崩（并行开发友好） |
| 3 | `backend/app/api/deps.py` | `require(Perm.X)`（权限依赖）、`get_context`（解析当前工作区）、越权审计用**独立会话**写 |
| 4 | `backend/app/api/v1/exceptions.py:161-180` | 端点本体只有 8 行：取权限上下文 → 调 Service → 决定 200/202 |
| 5 | `backend/app/services/exceptions.py:325-380` | Service 里的编排：版本校验 → 复用判断 → 并发保护 → **状态机校验** → 落库 |

**一次请求的完整旅程**（以 `POST /api/v1/exceptions/{id}/analyze` 为例）：

```text
HTTP 请求
 → main.py 中间件：生成 X-Request-Id，挂到 request.state
 → deps.get_context：解 JWT → 取用户 → 解析 X-Workspace-Id → 校验成员资格 → 构造 Repos(workspace_id)
 → deps.require(Perm.EXCEPTION_HANDLE)：角色权限不足 → 独立会话写审计 + 403
 → api/v1/exceptions.analyze_exception：只做参数与状态码（202=新建 / 200=复用）
 → services.ExceptionService.request_analysis：
       check_version（乐观锁）
       input_hash + _reuse_candidate（15 分钟内同输入直接复用，省 token）
       find_running（已有任务在跑 → 409 AI_ANALYSIS_IN_PROGRESS）
       apply_transition(case, EXCEPTION, ANALYZING)  ← 状态机唯一入口
       bump_version + 落 ai_analysis + 写 exception_event + 写 audit
 → ai_bridge.execute_analysis → app/ai/runner（AI 层，只读工具 + guard）
 → repositories.base._scoped：所有 SQL 自动附加 workspace_id 过滤
 → MySQL
```

**本段必须记住的三条"护栏"（面试常问）**：

1. **Router 只做鉴权/参数/状态码**——业务编排一律在 Service。好处：同一段业务逻辑能被 API、AI Tool、定时 tick 三种入口复用。
2. **改状态只能走状态机**——`services/common.apply_transition` → `rules/state_machine.plan_transition`；非法流转统一 409 + `details.allowed`。
3. **AI 不许碰数据库**——`tests/ai/test_tools.py:63 test_tools_do_not_import_session_or_repository` 用 **AST 静态扫描**守住这条纪律（不是靠自觉）。

**段 1 自测题**（先自己想，再看答案）：

1. 为什么 `analyze` 有 200 和 202 两个成功码？
   <details><summary>答案</summary>202=真的新建了分析任务（异步语义）；200=命中 15 分钟内、同 `input_hash` 的已有结果，直接复用（省 token、可重复点）。前端两者都当成功处理。</details>
2. 为什么越权审计要用**独立会话**写？
   <details><summary>答案</summary>`get_db` 在抛错时会 `rollback()`，如果共用请求会话，403 前写的那条 `security.permission_denied` 会一起被回滚——审计就"看得见规则、看不见证据"。这是我实测发现并修掉的真 bug。</details>
3. 如果 Router 里直接写业务逻辑，会先坏掉什么？
   <details><summary>答案</summary>AI Tool 与 tick 复用不到这段逻辑，同一规则会出现第二份实现 → 两条路径行为不一致；而且权限/审计容易漏写。</details>

## 附录 · 三个真实踩坑（D3-11 面试实战素材，全部有实测证据）

面试官最爱问"你遇到过什么问题、怎么定位的"。下面三条都是本项目的真实现场记录，**每个都能讲 3 分钟**。

### ① MySQL 外键删除顺序：SQLite 绿、MySQL 红

- **现象**：seed 的"清空工作区"逻辑在 SQLite 上一直绿；换到真 MySQL 清库时 `1451 Cannot delete or update a parent row`。
- **根因**：先删 `ai_analysis` 再删 `approval`，而 `approval.analysis_id → ai_analysis.id` 是 RESTRICT；SQLite 默认**不强制外键**，所以本地永远发现不了。
- **修法**：调整删除顺序（子表先删）；并加一条 `PRAGMA foreign_keys=ON` 的 SQLite 回归用例把差异"补齐"。
- **一句话价值**："测试库和生产库的行为差异会掩盖真 bug，所以我给 SQLite 打开了外键校验，并让 CI 在真 MySQL 上跑一遍。"

### ② 元数据锁自锁死：MySQL 上 pytest 永久挂起

- **现象**：`TEST_DATABASE_URL` 指向 MySQL 后，pytest 36 分钟只完成 30/344，进程 CPU 只有 27s，MySQL QPS = 0。
- **定位**：`information_schema.processlist` → 一条连接 `state=Waiting for table metadata lock`，`time=2148s`，卡在 `ALTER TABLE knowledge_chunk ADD FULLTEXT INDEX ...`。
- **根因**：`knowledge_index.reindex_all()` 在**未提交事务**里插入分片后，用**另一条连接**执行 ALTER；ALTER 需要排他元数据锁，被自己未提交事务持有的锁挡住，而 MySQL `lock_wait_timeout` 默认 31536000 秒（一年）→ 永不超时。
- **修法**：索引 DDL 回归 schema 阶段（alembic / `init-schema`），数据写入路径默认不做 DDL；确需补索引时先 `commit` 再建；`ensure_fulltext_index` 强制 `lock_wait_timeout=5`，拿不到锁就放弃并告警（检索退化 LIKE）。
- **结果**：MySQL 全量 343 passed + 1 skipped，7.4 分钟跑完。
- **一句话价值**："DDL 不能和未提交事务待在同一条路径上；我给所有可能等锁的操作都设了超时——**生产系统里没有'永久等待'这种合理行为**。"

### ③ 乐观锁用错版本号：验收脚本自己把自己挡在 409

- **现象**：一键验收在第 5 步 `analyze` 报 409 `OPTIMISTIC_LOCK_CONFLICT`。
- **根因**：脚本在第 4 步"录入承运商消息"后没有重新读异常详情，仍用旧 `version` 调 `analyze`——而录消息会让 `version` 自增。
- **修法**：调用前重新 `GET /exceptions/{id}` 取最新 `version`。
- **一句话价值**："这说明乐观锁真的在工作；同时也提醒我：**任何写操作前都要拿最新版本**，包括我自己的测试脚本。"

### ④ 跨层约定没有编译器保护：登录页域名写错，点演示账号必 401

- **现象**：登录页"演示账号"按钮填的是 `operator@demo.logiops`，而后端 seed 建的是 `operator@logiops.dev` → 点一下必然 `AUTH_INVALID_CREDENTIALS`。前端 `type-check`、`build`、后端 344 个测试**全都不会红**。
- **根因**：前后端各写一份"演示账号"字面量，没有任何机制保证一致（这是典型的"合约在两处、真相在两处"）。
- **修法**：① 统一为 seed 的真实域名；② 新增 `backend/tests/test_cross_layer_contract.py`：读 `frontend/src/views/LoginView.vue`，断言它覆盖 `app/seed/catalog.py::SEED_USERS` 的全部账号，并禁止旧域名再次出现。
  反向验证过：把域名改回错的，测试立刻红（`登录页缺少这些 seed 账号（点了会 401）`）。
- **一句话价值**："跨语言/跨仓的字面量约定，编译器帮不了你，只能靠契约测试钉住。我为此加了一条能复现这个事故的回归用例。"

### ⑤ 用 PowerShell 5.1 读写 UTF-8 文件：中文会被写坏

- **现象**：我用 `Get-Content -Raw` 读 `.vue` 文件、改完再 `Set-Content` 写回，中文注释全变乱码（`娉ㄦ剰锛?..`），并且吞掉一个换行导致 `error TS1128`。
- **根因**：Windows PowerShell 5.1 的 `Get-Content` **默认按 GBK 解码**（不是 UTF-8），再以 UTF-8 写回就是把中文"二次编码"；`Set-Content -Encoding UTF8` 还会加 BOM。
- **修法**：改文件一律用支持 UTF-8 的编辑器/工具；脚本里必须显式 `Get-Content -Encoding UTF8` / `Set-Content -Encoding UTF8`；改完 `.ps1` 要保留 BOM（否则中文脚本会被按 GBK 解析而语法报错）。
- **一句话价值**："Windows 上的编码问题不是小事——我因此踩过两次：一次是 `git add` 把临时目录带进提交，一次是把源码中文写坏。所以团队规范里要写清**统一的文件编码与提交前检查**。"
