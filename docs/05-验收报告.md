> **落地过程中修掉的三个真缺陷**（都由验收/真机暴露、均已加回归用例）：
> ① `tick` 把车推到终点后订单未 `DELIVERED`、异常被搁浅在 `PROCESSING`（"ETA=now 但订单仍在途"）；
> ② 维修等待口径丢失导致 ETA 被算成"立刻起程"，规则把 CRITICAL 错误降为 MEDIUM；
> ③ **元数据锁自锁死**：`ai/knowledge_index.reindex_all()` 在未提交事务里 flush 完分片后，
> 用**另一条连接**执行 `ALTER TABLE knowledge_chunk ADD FULLTEXT INDEX ...`；ALTER 需要排他元数据锁，
> 被调用方自己未提交事务持有的锁挡住，而 MySQL `lock_wait_timeout` 默认 31536000 秒（一年）→
> 永久挂起（实测 36 分钟只完成 30/344 个用例，连接 `state=Waiting for table metadata lock` 达 2148s）。
> 修复：索引 DDL 回归 schema 阶段（alembic / `init-schema`），`reindex_all` 默认不做 DDL 且新增
> `ensure_index=False` 显式开关；`ensure_fulltext_index` 执行 ALTER 前设 `lock_wait_timeout=5`，
> 拿不到锁就放弃并告警（检索退化 LIKE）。修复后 MySQL 全量 7.4 分钟跑完。
> 回归用例：`tests/unit/test_closure_regression.py`（4 条）+ `tests/integration/test_case_a_flow.py`（2 条）+ `tests/ai/test_knowledge.py`。

### 已知行为（不是缺陷，写清楚避免误判）

- 异常关闭后的 `level` 是**当前风险快照**：CASE-A 送达后影响解除，快照回落到 `MEDIUM`，而"曾达到 CRITICAL / risk 4"留在 `exception_event` 与 `exception.detected` 审计里。
  机器提议阶段（`DETECTED/CONFIRMING/ANALYZING`）则**只升不降**（`allow_downgrade=False`），不会把高危悄悄降级。
- 未进入处理阶段的异常遇到订单送达 → 直接 `CLOSED(close_reason=DELIVERED)`（状态机刻意没有 `CONFIRMING → RESOLVED` 这条边），同样不会"货到了异常还挂着"。
